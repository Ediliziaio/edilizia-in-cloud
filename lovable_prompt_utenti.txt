2. FIX CRITICO SICUREZZA — RLS `staff_permissions` (WITH CHECK mancante)
================================================================================

PROBLEMA: La policy RLS "Company admins can manage staff permissions" su
`staff_permissions` ha solo la clausola USING ma non WITH CHECK. Questo
significa che un admin può leggere SOLO i record della sua azienda ma può
SCRIVERE su qualsiasi riga del database (incluse righe di altre aziende).

FIX: Crea una nuova migration SQL che corregge la policy:

-- Nuova migration: fix_staff_permissions_rls_with_check.sql
ALTER POLICY "Company admins can manage staff permissions"
  ON public.staff_permissions
  USING (
    has_role(auth.uid(), 'company_admin'::app_role)
    AND company_id = get_user_company_id(auth.uid())
  )
  WITH CHECK (
    has_role(auth.uid(), 'company_admin'::app_role)
    AND company_id = get_user_company_id(auth.uid())
  );

Assicurati che questa migration venga applicata correttamente.

4. FIX — Generazione password in `supabase/functions/create-company-staff/`
================================================================================

PROBLEMA: La funzione `generateTemporaryPassword()` usa `Math.random()` che
non è crittograficamente sicuro. Anche per una password temporanea, è buona
pratica usare l'API crypto di Deno.

FIX: Sostituisci la funzione con questa implementazione sicura:

  function generateTemporaryPassword(): string {
    const chars = "ABCDEFGHJKLMNPQRSTUVWXYZabcdefghjkmnpqrstuvwxyz23456789!@#";
    const array = new Uint32Array(12);
    crypto.getRandomValues(array);
    return Array.from(array, (n) => chars[n % chars.length]).join("");
  }

(Deno ha `crypto` globale, nessun import necessario)

NOTE TECNICHE IMPORTANTI
================================================================================

- Database: Supabase (Postgres) con RLS abilitato
- Ruoli nel sistema: super_admin, company_admin, company_staff, salesperson,
  call_center (enum `app_role`)
- salesperson e call_center hanno ENTRAMBI i ruoli nel DB user_roles:
  es. salesperson → ["salesperson", "company_staff"]
  Questo perché la staff_permissions row viene creata solo se l'utente ha
  il ruolo company_staff. Quindi anche salesperson/call_center l'hanno.
- La funzione `has_permission(user_id, permission)` in PostgreSQL è usata
  nelle RLS di altre tabelle per controllare i permessi granulari.
- La funzione `get_user_company_id(auth.uid())` restituisce il company_id
  dell'utente corrente.
- Non creare nuove tabelle. Usa solo lo schema esistente.
- Usa sempre React Query (useQuery/useMutation) per le operazioni dati.
- Usa i componenti shadcn/ui esistenti (Switch, Checkbox, Badge, Dialog, ecc.)
