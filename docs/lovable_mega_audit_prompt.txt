Problemi comuni da cercare e correggere:

1. QUERY DIPENDENTI MALFORMATE:
   - Pattern pericoloso: query con `enabled: !!ordersRaw && ordersRaw.length > 0`
     che usa dati di un'altra query nell'array .map() DENTRO queryFn
   - Quando ordersRaw è stale e la seconda query riutilizza il closure,
     i dati possono desincronizzarsi
   - SOLUZIONE: assicurarsi che il queryKey includa un hash degli IDs,
     oppure usare `select` di React Query per derivare i dati

2. QUERYKEY INCOMPLETO:
   - Ogni queryKey che dipende da filtri, date, o parametri variabili DEVE
     includere quei valori nella key
   - Esempio: ["margin-orders", companyId] — OK
   - Esempio: ["margin-orders"] senza companyId — BUG (cross-tenant data leak)
   - Verifica TUTTI i queryKey negli hook e aggiungi eventuali parametri mancanti

3. ENABLED FLAG MANCANTE:
   - Ogni query che dipende da companyId deve avere `enabled: !!companyId`
   - Cerca query senza il flag enabled che potrebbero girare con companyId null

4. STALE TIME INCOERENTE:
   - Allinea staleTime in tutto il codebase: usa 5 * 60 * 1000 (5 min) come default
   - Per dati critici (auth, profile): 0 o Infinity solo se intenzionale
   - Per dati amministrativi che cambiano raramente: 10 * 60 * 1000 (10 min)

5. MISSING ERROR HANDLING:
   - Ogni queryFn che fa `if (error) throw error` è corretto
   - Ma verifica che i componenti consumatori gestiscano lo stato `isError`
     mostrando almeno un Alert o un fallback invece di crashare

6. MEMORY LEAK nelle query annidate:
   - Il pattern "query A che abilita query B tramite .map()" in useBreakEvenHistorical
     e useMarginData: verifica che quando orderIds è un array vuoto [], la query
     non parta comunque (in("order_id", []) in Supabase genera una query invalida)
   - Aggiungi `enabled: orderIds.length > 0` (non solo `> 0` ma controllo esplicito)

Ottimizzazione:
- Crea src/lib/queryKeys.ts con costanti per tutti i queryKey dell'app, es:
  ```
  export const QUERY_KEYS = {
    marginOrders: (companyId: string | null) => ["margin-orders", companyId],
    employees: (companyId: string | null) => ["margin-employees", companyId],
    // ... tutti gli altri
  }
  ```
  Questo previene typo nei queryKey e facilita l'invalidation

Problemi da cercare:

1. TIPO `any` ESPLICITI:
   - Cerca tutti i casi di `: any` o `as any` nel codice
   - Ogni `any` è un potenziale runtime bug nascosto
   - Sostituisci con tipi specifici o con `unknown` + type guard

2. NON-NULL ASSERTION AZZARDATA:
   - Cerca tutti i `!` non-null assertion (es. `user!.id`, `company!.name`)
   - Ogni `!` senza un controllo precedente è un potenziale crash
   - SOLUZIONE: sostituisci con optional chaining `?.` + fallback `?? defaultValue`
   - Eccezione OK: `enabled: !!companyId` nelle query (questo è corretto)

3. TYPE GUARD MANCANTI:
   - In useMarginData.ts: `const customer = order.customer as { first_name: string; last_name: string } | null`
   - Questo cast "fiducioso" può fallire se lo schema Supabase cambia
   - SOLUZIONE: aggiungi una type guard:
     ```
     function isCustomerProfile(obj: unknown): obj is { first_name: string; last_name: string } {
       return typeof obj === 'object' && obj !== null && 'first_name' in obj
     }
     ```

4. ENUM vs UNION TYPE:
   - Verifica che AppRole sia usato come union type (non enum TypeScript)
     perché gli enum generano codice JS extra inutile
   - `type AppRole = "super_admin" | "company_admin" | ...` ✓ CORRETTO
   - `enum AppRole { super_admin = "super_admin", ... }` ✗ DA CAMBIARE

5. DATABASE TYPES:
   - In src/integrations/supabase/types.ts ci sono i tipi auto-generati
   - Verifica che gli hook usino i tipi database (`Database['public']['Tables']['orders']['Row']`)
     invece di tipi ridefiniti manualmente che potrebbero disallinearsi

6. RETURN TYPE ESPLICITI:
   - Tutti gli hook custom devono avere return type esplicito
   - Questo previene che modifiche interne cambino silenziosamente l'interfaccia
   - Esempio: `export function useMarginData(): MarginData { ... }` ✓
